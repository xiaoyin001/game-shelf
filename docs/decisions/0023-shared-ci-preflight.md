# ADR-0023：共用有界 CI 环境与提交绑定的本地预验收

状态：采用（2026-10-23，共用运行器本地候选源码/race、完整test:ci与额外新DB浏览器通过；pre-push独立切片尚未安装，新SHA云端未验收）。完整Playwright基底准备超时后的替换见 [ADR-0024](0024-headless-ci-image.md)，原尝试与失败保留。接续 [ADR-0012](0012-reproducible-ci.md) 的同入口目标，替换本地临时工具容器与云端原生工具安装的双路线；保留 [ADR-0013](0013-mongodb-kernel-compatibility.md) 的宿主内核限制和 [ADR-0022](0022-ci-render-budget.md) 的真实 WebGL2、30秒/零重试及分层期限。

## 背景
用户指出连续三次推送后才暴露 CI 失败。已证实的差异包括宿主内核、双窗口软件绘制资源竞争、冷安装与总期限；首次缺少现场的 MongoDB 故障仍不能追认根因。更根本的执行缺口是：后续阶段用 `test:all` 加忽略目录里的临时脚本代替完整 `test:ci`，未完整复跑正式安装和故障回收；本地通过没有绑定待推送提交，也未强制检查资源和用例余量。这是验收制度和实现问题，不推给网络或 owner。

最新已推送3e65411的 [CI39792750622](https://github.com/xiaoyin001/game-shelf/actions/runs/39792750622) 已核对源码/race、19/19浏览器及正常/故障零残留全部成功；这只证明该次提交，不证明原流程足以预防下一次差异。

## 比较
- 只补规范或继续使用临时脚本：容易漏执行、无法从克隆仓库复跑，不采用为完整方案。
- 只用 act 执行 YAML：增加第三方模拟器/镜像，不能复刻真实宿主内核和网络，未实测，不采用。
- 特权 Docker-in-Docker：隔离端口方便，但需要更高权限并维护第二个 daemon，当前不采用。
- 本地与 CI 共用固定 digest 的工具镜像、资源/期限配置及运行器，再增加提交绑定的防漏检门禁：采用。复用现有 Docker/Compose 和真实 `test:ci`，不换数据库、不关闭图形或缩小业务验收。

## 决定
1. 两个 Docker 构建目标：source 使用官方 Go1.25.0-bookworm（包含真实 CGO/race 编译工具）及 Node22.23.3；playable 使用官方 Playwright1.64.1-jammy、相同 Go/Node 与 Docker29.1.3 CLI/Compose。四个基础镜像均锁定 registry digest、固定 linux/amd64，不在不同机器临时 apt 安装不同图形库。playable 明确 CGO=0，source 强制 CGO=1 并执行全量 race；不以无CGO绕过race。Playwright官方完整镜像的amd64压缩层约891.7MiB（registry元数据），会下载未使用的浏览器，实际运行仍仅默认headless shell；首次下载/构建耗时未实测。
2. 本地与 GitHub 使用同一版本化入口；每个测试工具容器限制2 CPU、4GiB内存且不使用swap，并实际检查cgroup及绑定两个CPU。数据库在CI覆盖配置内也有资源上限。宿主仍共享内核，继续拒绝当前Mongo组合的未验收内核；容器不能使WSL内核变成Azure内核。
3. 每job独立空 npm/Go模块/编译缓存与临时源码副本，playable两轮使用新的DB project和空卷；同job第二轮允许复用本轮已按锁文件校验的工具缓存，不复用任何开发/上轮运行缓存，避免重复下载不可变依赖耗尽行为预算。固定镜像层可以缓存且如实记录，不清全局缓存/镜像。source执行原规则/历史/Go/客户端及race；playable初拟连续两轮完整 `test:ci`，实际预算失败后由ADR-0024的独立条目调整为一次完整回归及额外一次新DB浏览器，保留全部原覆盖。任一轮失败整次失败，不是失败后重试择优。
4. 安装/构建10分钟、执行12分钟（其中预留1分钟退出取证）、每job总预算25分钟继续成立。浏览器每例仍30秒、零重试、单worker；另用实际JSON报告检查至少当前19例全部成功、零跳过/重试，最慢用例不超过27秒，保留至少3秒调度余量。阈值与资源从仓库单一配置读取，不让本地和CI各自维护。
5. 在自建临时Git副本执行：正式模式只接受干净HEAD；提交前候选模式只测试已暂存且无未暂存改动的tree，不产生可推送结论。复制Git对象但不复制源仓库配置/凭据；不将主机HOME、GitHub凭据或开发库挂入工具容器。仅playable挂本机Docker socket，属于可信仓库测试权限，不能用于不可信第三方代码。使用host网络复用现有localhost协议，端口占用直接拒绝，不自动停止试玩。
6. 正常/失败/超时均保存证据并按本轮随机ID清理；外层知道正向与故障project名字，即使工具容器中断也只回收本轮资源，独立核对零残留。Windows通过WSL Docker使用同一入口并保持本轮WSL前台存活，不改共享系统库。长命令使用控制管道/独立Linux进程组，EOF后TERM并限时KILL，不能依赖结束wsl.exe就代表Linux任务已退出；专有分支在Windows实际验证，Linux不冒充已执行。
7. 在共用运行器完整通过后，单独完成本地pre-push防漏检：报告绑定commit/tree、配置、环境、结果及时间，正式验证通过才允许申请Push。hook不替代owner的每次授权，也不是阻止恶意绕过的安全边界。实现/验收前不宣称已安装门禁。

### Windows/WSL网络的附加决定（实现前记录）
首次全新工具构建在10分钟内未完成Node基础镜像拉取，失败证据在本地保存；不是通过记录。已核实Windows有HTTP代理、Docker daemon未配置代理，WSL连接该Windows回环地址立即拒绝。不能靠沿用旧工具镜像或无限加时绕过。

比较：保持daemon直连会重复阻塞；修改共享daemon/代理设置并重启会影响其他任务，不采用；采用固定版本regctl0.11.7客户端，通过主机已有代理导出**同一固定digest**的官方OCI内容，再由标准Docker加载，registry内容校验不改变。regctl二进制也固定官方release SHA256，不读主机私有registry凭据。只在主机显式提供HTTP代理时使用此传输，不改变云端正常Docker下载；下载/导入仍计入10分钟准备期限。运行时临时桥接到已有回环代理：直接访问Windows虚拟网卡的探测也超时，因此采用Windows主动连接WSL的反向通道，WSL代理入口仅监听回环，回传入口仅监听WSL虚拟网卡并限制Windows网关源IP和一次性令牌；不记录代理内容，结束关闭。无需修改防火墙/系统代理，不面向物理LAN提供开放代理。代理地址不写入报告或Git，只传子进程环境；当前不接收带用户名/口令的代理，不读取私有registry凭据。尚未实测吞吐和完整验收，不预填成功。

## 验证
先用单元测试覆盖参数、范围、资源读取、报告余量和候选/正式状态；再在本机真实Docker完整跑source与两轮playable，核对实际CGO/race、CPU/内存、19例/每例时长、正常和故障零残留及截图。测试外层中断回收和端口保护。阶段完成分别记录实际命令、失败及未覆盖项；旧3e65411云端成功不算新入口通过。Push需另获授权，新SHA GitHub成功才算远端闭环。

## 代价、迁移与回退
工具镜像和两轮验收增加首次下载、磁盘及运行成本，未做统计性能/成本横评。Docker socket具备本机daemon权限，仅运行可信本项目脚本；不启用特权容器、不发布新的远端镜像、不清共享数据。CI仍使用Ubuntu22.04宿主跑playable、24.04宿主跑source，用户态由固定工具镜像决定；22.04退役及Mongo修复重评期限仍有效。

迁移仅更换CI工具执行方式，业务协议/资源/帐号与试玩不迁移。可整套回退共用运行器并恢复原YAML工具步骤，但必须保留完整test:ci与真实远端复验，不能删除测试或把test:all继续当推送充分证据。没有任何本地环境能保证远端永不失败：Azure内核、网络、宿主负载及Actions服务仍须按实际SHA观察并取证。

## 重评条件
若镜像首次下载超过预算，先记录具体阶段/吞吐，再比较只含headless shell的专用工具镜像及其维护成本，不未经授权发布镜像或盲目加时。若2CPU/4GiB无法完成现有测试，先定位真实资源需求/泄漏/长用例，不加重试、不抹去失败。若hook频繁被绕过或团队扩大，再评估远端保护规则，需额外授权。
