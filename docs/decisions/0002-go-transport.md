# ADR-0002：Go 与可验证的 TCP 基础

状态：采用。兼容桥后续使用的 google.golang.org/protobuf v1.36.5 在新增连续标量中暴露 presence 问题，补丁升级由 [ADR-0020](0020-protobuf-scalar-presence.md) 替代；原帧、协议与 v1.5.4 消息接口不变。

## 背景
当前只有协作规则。下一步需要独立验证的通信库，为后续服务链路提供清晰边界，不提前加入账号、世界或客户端。

## 比较
- Node/TypeScript：客户端与服务器语言统一，但会偏离已验收版本的 Go 服务与运行方式。
- C# 或 Rust：适合特定性能或引擎需求，当前没有证据证明引入新工具链有收益。
- Go：采用，已有可玩目标使用 Go，当前环境可原生构建与测试，并发与网络测试工具直接可用。不是声称 Go 比其他语言性能更高，未做性能横评。

通信比较 HTTP/JSON、gRPC 与既有自定义 TCP + protobuf：本轮保留 16 字节大端头、请求序号关联和 protobuf 体，保证后续目标兼容。代价是需要自己验证长度限制、截止时间、错误响应和连接退出，而不是免费获得完整 RPC 框架。

## 决定
先只实现协议与通用请求响应传输，复用已经理解的基础算法，但在新仓库重新加入测试并执行；不整包带入旧版业务契约。
服务调用必须尊重 context 截止时间；取消服务会关闭空闲连接。Go 1.25 和 protobuf 1.5.4 固定为本阶段工具与消息接口，更多依赖按下一阶段需要引入。

## 验证
增加帧字节序、短包、超大包、protobuf 往返、context 截止时间及空闲连接取消测试。npm run check 从本阶段起包含规则检查、Go 格式检查、测试、vet 与构建，不把库测试当游戏验收。

## 重评条件
如果出现协议增长、跨语言生成或调用并发瓶颈，再比较引入 schema 生成或成熟 RPC，另立 ADR 明确兼容迁移。当前不预建这些能力，也没有吞吐容量结论。
